# 아키텍처 노트

## 원장

모든 잔고 변경은 `LedgerService.post`를 거칩니다. 다른 코드는 `ledger_accounts.balance`를 직접 바꾸지 않습니다.

- **금액 단위**: 코인은 자산의 최소 단위 정수(BTC는 satoshi, ETH는 wei)로, 법정화폐는 최소 단위 정수(KRW는 원, USD는 센트)로 저장합니다. 소수점 연산은 하지 않습니다.
- **계정**: 이용자마다 자산별로 `available`(가용), `escrow`(에스크로 잠금), `withdrawal_pending`(출금 대기) 계정이 있습니다. 시스템 계정은 `custody`(온체인 보관분의 상대 계정)와 `fee_revenue`(수수료 수익)입니다.
- **복식부기**: 한 거래의 분개 합은 자산별로 항상 0입니다. 서비스에서 먼저 검사하고, DB의 지연 제약 트리거가 커밋 시점에 다시 검사합니다.
- **음수 잔고 금지**: 이용자 계정은 CHECK 제약으로 0 미만이 될 수 없습니다. 잔고가 부족하면 `insufficient_balance` 오류가 나고 트랜잭션 전체가 롤백됩니다.
- **멱등성**: 모든 거래에 `idempotency_key`가 있어서 같은 키로 두 번 요청해도 한 번만 반영됩니다.
- **잠금 순서**: 계정은 id 순으로 잠가 동시 요청 사이의 교착을 막습니다. 주문 흐름에서는 주문, 광고, 원장 계정 순서로 잠급니다.
- **변경 불가 기록**: `ledger_entries`, `ledger_transactions`, `audit_logs`는 UPDATE와 DELETE를 트리거로 막습니다.
- **대사**: `findMismatchedAccounts`는 저장된 잔고와 분개 합이 다른 계정을 찾습니다. 일 대사 작업에서 결과가 비어 있어야 정상입니다.

## 주문 번호

화면, 알림, 메일, 운영 콘솔에는 `orders.order_number`를 보여 줍니다. 주문 날짜(한국 시간) `YYYYMMDD`에 그날의 4자리 일련번호를 붙인 값입니다(예: `202610260001`). 일련번호는 매일 0001부터 다시 시작하고, 하루 9,999건을 넘으면 다섯 자리로 늘어납니다(`2026102610000`). 기본 키와 URL은 그대로 uuid입니다.

번호는 주문을 넣는 트랜잭션 안에서 `next_order_number()`가 `order_number_counters`의 그날 행을 올려 받습니다. 그 행은 트랜잭션이 끝날 때까지 잠기므로 동시에 들어온 주문도 번호가 겹치지 않고, 실패한 주문은 번호를 돌려줘 빈 번호가 생기지 않습니다.

## 주문 상태

PRD 6.4가 없어서 아래 상태는 PRD 5장의 흐름을 바탕으로 정했습니다. 허용 전이는 `apps/api/src/orders/order-state.ts`에 한곳에 모여 있습니다.

| 이벤트 | 누가 | 이전 상태 | 다음 상태 | 에스크로 |
| --- | --- | --- | --- | --- |
| 주문 생성 | 테이커 | - | `pending_payment` | 판매자 가용 → 에스크로 |
| `mark_paid` | 구매자 | `pending_payment` | `paid` | 변화 없음 |
| `release` | 판매자 | `pending_payment`, `paid` | `completed` | 에스크로 → 구매자 가용 |
| `cancel` | 구매자 | `pending_payment` | `cancelled` | 에스크로 → 판매자 가용 |
| `expire` | 시스템 | `pending_payment` (기한 초과) | `cancelled` | 에스크로 → 판매자 가용 |
| `escalate` | 구매자, 판매자 | `paid` | `under_review` | 변화 없음 |
| `auto_review` | 시스템 | `paid` (정해진 시간 동안 릴리즈 없음) | `under_review` | 변화 없음 |
| `resolve_release` | 운영자 | `under_review` | `completed` | 에스크로 → 구매자 가용 |
| `resolve_refund` | 운영자 | `under_review` | `cancelled` | 에스크로 → 판매자 가용 |

- 판매자는 구매자가 결제 완료를 누르기 전에도 입금을 확인했다면 릴리즈할 수 있습니다.
- 구매자는 결제 완료를 누른 뒤에는 취소할 수 없습니다. 이후 분쟁은 운영 검토로 갑니다.
- 구매자가 결제 완료를 누른 뒤 `orders.auto_review_minutes`(기본 10분, `정책 설정`에서 변경) 안에 판매자가 릴리즈하지 않으면 주문 만료 워커가 `auto_review`로 운영 검토에 넘기고 두 당사자에게 알립니다. 누가 검토로 보냈는지는 `review_source`(`buyer`, `seller`, `system`)와 `escalated_at`에 남고, 분쟁 목록과 대시보드에 `자동 전환`으로 표시됩니다.
- 정산 분개는 주문당 `order:{id}:settle` 키 하나를 씁니다. 릴리즈와 반환이 동시에 와도 한쪽만 반영됩니다.

## 수수료

광고주(메이커) 수수료는 가격에 % 요율을 더하는 방식이고, 원화로 받습니다. 테이커 수수료는 없습니다.

- 요율은 `fee_rates`에 0.01% 단위 정수(25 = 0.25%, 최대 10%)로 쌓습니다. 마켓(코인 × 법정화폐)별 요율이 없으면 기본 요율을 씁니다. 변경은 지우지 않고 `effective_from`이 있는 새 행으로 남기므로 예약 변경과 이력 조회가 됩니다. 운영 콘솔 `정책 설정`에서 바꿉니다.
- 마켓에 보이는 가격 = 입력 가격 + ⌈입력 가격 × 요율⌉. 주문할 때 `코인 값 = ⌊수량 × 입력 가격⌋`, `수수료 = ⌈코인 값 × 요율⌉`, 구매자 이체액 `fiat_amount_minor = 코인 값 + 수수료`이고, 요율·입력 가격·수수료를 주문에 고정합니다(`fee_rate_bp`, `base_price_minor`, `fee_fiat_minor`). `price_minor`는 수수료를 더한 최종 가격입니다.
- 판매 광고와 구매 광고에 같은 규칙을 씁니다. 코인에서는 떼지 않으므로 판매자가 잠그는 수량과 구매자가 받는 수량이 같습니다. `fee_amount`(코인 수수료)는 이전 주문 기록용으로만 남아 있습니다.
- 완료된 주문의 수수료는 청구 대상이 됩니다. 취소·반환된 주문은 수수료가 없습니다.

### 청구

- `BillingWorker`(기본 5분, `BILLING_INTERVAL_SECONDS`)가 청구 주기(일 또는 월, 한국 시간 기준, 기본 월)가 끝난 수수료를 광고주·통화별로 묶어 `fee_invoices`를 만들고 주문에 `fee_invoice_id`를 답니다. 납부 기한은 발행일 + `billing.due_days`(기본 7일)의 하루 끝입니다. 두 값은 `ops_settings`에 있고 `정책 설정`에서 바꿉니다.
- 기한 전날과 당일에 알림·이메일을 보내고, 기한이 지나면 `overdue`로 바꿉니다. 연체 청구서가 있는 광고주의 광고는 마켓에 안 보이고, 그 광고로 주문할 수 없고, 새 광고도 올릴 수 없습니다(`fee_overdue`). 완납하면 바로 풀립니다.
- 입금은 시스템 밖에서 확인하고, 심사자가 `fee_payments`에 금액·일시·메모를 기록합니다(step-up 필요). 일부 납부는 남은 금액이 미납으로 남고, 연체 청구서는 완납해야 `paid`가 됩니다. 플랫폼 계좌 관리와 세금계산서 발행은 하지 않습니다.

## 결제수단

- 가입 때 받는 이름(`users.first_name`, `last_name`)은 회원이 직접 적은 값이라 검증되지 않습니다. 화면 표시와 운영 검색에만 쓰고, 예금주 대조에는 쓰지 않습니다.
- 계좌 예금주는 KYC 실명(`users.legal_name`)과 같아야 등록됩니다. 공백, 대소문자, 전각 문자 차이는 같은 이름으로 봅니다. 제3자 계좌로 입금받는 것을 막기 위한 규칙입니다(PRD 11장).
- 계좌번호는 암호화해 저장하고, 목록에는 끝 4자리만 보여 줍니다. 전체 번호는 진행 중인 주문의 두 당사자에게만 보입니다.
- 회원당 입금 계좌는 1개입니다(`payment_methods_one_active_idx`). 계좌를 바꾸면 기존 행은 `removed`가 되고 새 행이 생기며, 닫히지 않은 내 광고는 새 계좌를 가리키도록 옮깁니다.
- 등록한 계좌는 바로 쓸 수 있습니다. 쿨다운은 `PAYMENT_METHOD_COOLDOWN_HOURS`로 켤 수 있고(기본 0), 켜면 처음 등록한 계좌는 그 시간이 지나야 쓸 수 있습니다. 계좌를 변경하면 새 행이 기존 행의 `cooldown_from`을 이어받아 쿨다운이 다시 시작되지 않습니다.
- 주문은 생성 시점의 판매자 계좌를 `seller_payment_method_id`로 고정합니다. 이후 계좌를 바꾸거나 지워도 진행 중인 주문의 입금처는 바뀌지 않습니다.
- 1원 송금 같은 계좌 실소유 확인은 업체 연동 후 추가합니다.

## 출금

- 상태: `requested`(운영 검토 대기) → `approved`(커스터디로 넘길 준비) → `sent`(전송) → `confirmed`(완료). 검토 중 `rejected`·`cancelled`, 전송 실패 시 `failed`가 되며 이 세 경우 코인은 `available`로 돌아갑니다.
- 신청 시 `수량 + 수수료`를 `available`에서 `withdrawal_pending`으로 옮깁니다. 완료되면 수량은 `custody`로, 수수료는 `fee_revenue`로 갑니다(원장 키 `withdrawal:{id}:lock`, `withdrawal:{id}:settle`).
- 자동 승인 기준(`autoApproveMax`) 이하는 바로 `approved`, 넘으면 운영자 검토로 갑니다. 운영자 승인·거절과 커스터디 콜백(`markSent`, `markConfirmed`, `markFailed`)은 서비스에만 있고, 운영 도구와 커스터디 연동 때 HTTP로 엽니다.
- 한도는 KYC 단계별·코인별 24시간 누적(거절·취소·실패 건 제외)입니다. 같은 사용자의 신청은 사용자 행 잠금으로 직렬화해 동시 신청으로 한도를 넘을 수 없습니다.
- 출금은 화이트리스트에 등록하고 쿨다운이 지난 주소로만 갈 수 있습니다. KYC 단계별 24시간 한도가 있고 KYC 0단계는 출금할 수 없습니다. `withdraw_held`나 `closed` 상태 계정은 출금할 수 없습니다.
- 수수료·최소 수량·자동 승인 기준·KYC 단계별 한도는 `withdrawal_rules`, `withdrawal_daily_limits` 테이블에 있고 운영 콘솔 `정책 설정`에서 바꿉니다. 출금 신청마다 DB에서 읽으므로 바꾼 값은 다음 신청부터 적용됩니다. 원화 환산 한도는 시세 피드가 붙은 뒤에 바꿉니다.
- 주소 검사는 형식만 봅니다(비트코인 bech32/base58, 이더리움 0x+40자리). 체크섬 검증은 커스터디 연동 때 서명 전에 한 번 더 합니다.

## 운영 콘솔

- 운영자는 `operators` 테이블에 따로 있고 세션(`operator_sessions`, 기본 8시간)과 로그인 기록도 이용자와 분리합니다. 이용자 토큰은 `/ops`에서, 운영자 토큰은 이용자 API에서 통하지 않습니다. 웹도 쿠키를 따로 씁니다(`p2p_ops_session`).
- 로그인할 때마다 OTP가 필요합니다. 계정은 운영 콘솔의 관리자 관리(administrator만)나 CLI로 만들고, 새 계정의 OTP 비밀키는 만들 때 한 번만 보여 줍니다.
- 역할은 `reviewer`와 `administrator` 둘입니다. administrator는 reviewer 권한에 더해 마켓 상태, 청구 실행, 운영자 계정(등록, 수정, 역할 변경, 사용 중지, 삭제, 비밀번호·OTP 재설정)을 관리합니다. 2인 승인은 없고 reviewer 한 명이 바로 처리합니다.
- 활성 administrator가 적어도 한 명은 남아야 합니다. 마지막 administrator를 내리거나 멈추거나 지울 수 없고, 자기 역할·상태는 다른 administrator가 바꿉니다. 삭제한 운영자는 `status = 'deleted'`로 남겨 감사 로그와 지난 결정에 이름이 계속 보입니다.
- 분쟁 해결은 reviewer가 사유와 함께 결정하면 같은 트랜잭션에서 주문을 `completed`/`cancelled`로 바꾸고 에스크로를 옮긴 뒤 `dispute_resolutions`에 기록합니다.
- 분쟁 결정, 출금 승인, 출금 한도 변경, 계정 해지는 재확인(step-up)이 필요합니다. 새 OTP 코드를 넣으면 그 세션의 `step_up_until`이 5분 뒤로 잡힙니다. 코드는 로그인과 같은 카운터를 써서 한 번만 쓸 수 있습니다.
- 설정 변경은 감사 로그에 변경 전·후 값을 함께 남깁니다. 감사 로그의 `target_id`는 회원·주문 ID뿐 아니라 코인 코드 같은 설정 키도 담도록 text입니다.
- 계정 제한: `trade_suspended`는 주문을, `withdraw_held`는 출금을, `closed`는 로그인을 막습니다. 진행 중인 주문과 출금은 그대로 둡니다.
- 운영자 동작마다 `audit_logs`에 `actor_type = 'operator'`로 남습니다.

## 알림

- 알림은 원인이 된 변경과 같은 트랜잭션에서 `notifications`에 씁니다. 변경이 롤백되면 알림도 남지 않고, 커밋되면 반드시 남습니다.
- 받는 사람: 주문은 거래 당사자 중 방금 행동한 사람을 뺀 쪽(시스템이나 운영자가 바꾼 경우 둘 다), 출금은 본인(자동 승인은 제외), 계정 제한은 본인입니다. 운영자가 적은 제한 사유는 이용자에게 보내지 않습니다.
- 이메일은 종류별 템플릿(한국어·영어, `users.locale`)으로 `email_outbox`에 쌓고, `EmailWorker`가 `EMAIL_INTERVAL_SECONDS`마다 보냅니다. 실패하면 1·2·4·8분 간격으로 다시 시도하고 5번째에 `failed`로 둡니다. 채팅 메시지 알림은 앱 안에서만 보입니다.
- 메일은 Resend(`RESEND_API_KEY`, `EMAIL_FROM`)로 보냅니다. 키가 없으면(로컬 개발, 데모) `LogEmailSender`가 보내는 대신 내용을 로그에 남깁니다.
- 가입은 이메일 인증 없이 바로 계정을 만들고 로그인합니다. 한때 이메일 인증을 거쳤기 때문에 그 시기에 인증한 회원만 `users.email_verified_at`이 찍혀 있고, 다른 회원은 비어 있습니다. 어느 쪽이든 로그인·거래에 차이는 없습니다. 인증을 없앨 때 아직 링크를 기다리던 가입 신청은 계정으로 옮겼습니다(migration 022).
- 발송은 최소 한 번 보장입니다. 보낸 직후 DB 커밋이 실패하면 같은 메일이 다시 갈 수 있습니다.

## 화면 언어

- 고객 화면은 한국어와 영어를 지원합니다. 운영 콘솔은 한국어만 씁니다.
- 한국어가 원문입니다. 컴포넌트는 `t('한국어 문장')`을 부르고, 영어는 `apps/web/lib/en.ts`에서 한국어 문장을 키로 찾습니다. 변수는 `{asset}`처럼 씁니다.
- 언어는 `p2p_lang` 쿠키로 정하고, 쿠키가 없으면 브라우저 언어(`ko`면 한국어, 아니면 영어)를 따릅니다. 로그인한 사용자가 언어를 바꾸면 `users.locale`에도 저장해 이메일 언어가 같이 바뀝니다.
- 웹 테스트가 고객 화면 파일을 훑어서, 마크업에 한국어가 직접 들어갔거나 영어 번역이 빠진 문장이 있으면 실패합니다. 새 문구를 추가하면 `en.ts`에도 넣어야 합니다.

## 아직 정하지 않은 것

- 판매 광고 등록 시 코인을 미리 잠글지(AD-5): 지금은 주문 생성 시점에 잠급니다.
- 변동가 광고(AD-3): 시세 피드가 붙으면 주문 시점 가격을 계산해 `price_minor`에 고정합니다.
- 결제 완료 후 판매자가 응답하지 않을 때 자동으로 운영 검토로 넘길 시간.

## 마켓과 코인 상태

- 마켓은 `markets`(코인 × 법정화폐)에 `open`, `paused`, `closed` 상태로 있습니다. `open`이 아니면 새 광고와 새 주문을 막고(`market_unavailable`) 마켓 목록에서 광고를 숨깁니다. 진행 중인 주문은 그대로 끝까지 갑니다.
- 코인 상태(`assets.status`): `ads_paused`는 새 광고만, `withdrawals_paused`는 새 출금만(`withdrawals_paused`) 막습니다. `delisted`는 새 광고, 주문, 출금을 모두 막습니다.
- 바꾸는 것은 administrator만 할 수 있고, 사유와 전·후 상태가 감사 로그에 남습니다.

## 운영 콘솔의 개인정보

- 회원 그리드와 상세는 전화번호(`010-****-5678`), 실명(`홍*동`), 가입 때 적은 이름, 계좌 예금주를 가려서 보여 줍니다. 전체 값은 사유를 적고 OTP를 다시 확인해야(`전체 보기`) 보이고, 그 열람이 `user.reveal_pii`로 감사 로그에 남습니다.
- 분쟁 화면은 입금자명과 예금주를 대조해야 하므로 당사자 실명을 그대로 보여 줍니다.


## 본인 인증 (Sumsub)

- KYC는 0(미인증)과 1(인증 완료) 두 단계뿐입니다. Sumsub 레벨은 하나(`SUMSUB_LEVEL_NAME`)만 쓰고, 출금 한도와 광고의 최소 KYC도 이 두 단계로 정합니다.
- 고객은 `내 계정 → 본인 인증하기`(`/account/verify`)에서 Sumsub WebSDK로 신분증과 얼굴 사진을 제출합니다. SDK 토큰은 서버가 Sumsub API로 만들고, 지원자는 우리 회원 ID(`externalUserId`)로 묶입니다. 시크릿 키는 브라우저로 가지 않습니다.
- Sumsub는 API 서버의 `POST /kyc/sumsub/webhook`으로 결과를 보냅니다. API가 외부에 열려 있지 않은 배포(Render 데모)에서는 웹 주소의 `/api/kyc/sumsub/webhook`으로 받습니다. 웹 프록시는 이 경로에 한해 서명 헤더(`X-Payload-Digest`, `X-Payload-Digest-Alg`)와 본문 바이트를 그대로 넘깁니다. 본문의 HMAC(`X-Payload-Digest`)가 `SUMSUB_WEBHOOK_SECRET`과 맞지 않으면 401로 버립니다. 같은 본문은 `sumsub_webhooks`에 한 번만 기록되고 다시 오면 무시합니다.
- 웹훅이 순서대로 온다고 믿지 않고, 받을 때마다 Sumsub에서 지원자를 다시 읽어 지금 상태를 반영합니다. 결과가 바뀐 경우에만 등급을 움직입니다. 승인(GREEN)이면 KYC 1과 신분증의 실명(`users.legal_name`)을 저장하고 알림을 보냅니다. 재제출 요청(RED/RETRY)은 알림만, 최종 거절(RED/FINAL)은 KYC를 0으로 내리고 알림을 보냅니다. 같은 결과가 다시 와도 운영자가 수동으로 바꾼 등급을 덮어쓰지 않습니다.
- 신분증 이미지와 문서 번호는 저장하지 않습니다. 운영자는 회원 상세의 KYC 탭에서 상태, 결과, 거절 사유, 마지막 갱신 시각을 보고, 원본은 Sumsub 콘솔 링크로 확인합니다. 웹훅이 빠졌을 때는 `Sumsub에서 상태 다시 가져오기`, 재심사가 필요하면 `재심사 요청`을 씁니다. 둘 다 감사 로그에 남습니다.
- 키는 환경변수로만 둡니다(`SUMSUB_APP_TOKEN`, `SUMSUB_SECRET_KEY`, `SUMSUB_WEBHOOK_SECRET`, `SUMSUB_LEVEL_NAME`). 넷 중 하나라도 없으면 본인 인증은 `kyc_unavailable`(503)을 돌려주고, 정책 설정 화면에 `키 미등록`으로 표시됩니다.
